# copyengine 0.4 design

Status: draft, updated as the design settles. 0.4 builds two things, in
this order:

1. **Tile IR**: copies whose unit is a group of elements instead of one
   element, so quantization with per-group scales (static or computed from
   the group's amax), dequantization and packing happen while copying.
2. **TMA / cp.async** (sm90+): bulk tile copies, also where copy kernels
   are confined to a few SMs.

It also carries what 0.3 left open: bandwidth limits for copies with device
indices, `segments` / `indices` through the C++ ops and as plan parameters,
less Python per `step(...)` call, transposes sized by element, and whether
copyengine still needs a pinned pool of its own.

## 1. Tile IR

### The model

Today a statement is `dst[D(i)] = f(src[S(i)])` over a domain of elements,
`f` a per-element function (cast, scale, clamp). 0.4 keeps that form and
changes what the domain is made of:

    dst_j[D_j(u)] = f_j(src_1[S_1(u)], ..., src_k[S_k(u)])   for each unit u

- A **unit** is `g` consecutive elements in the row-major order of the
  trailing dimensions of the data (a group of 128 along the hidden size, a
  whole token, a whole KV page). An element copy is the unit `g = 1`.
- Each access maps a unit to its part of a tensor: the data access to `g`
  elements, a scale access to one element (a projection of the domain: the
  unit index, with any strides; broadcast where several units share one).
- `f` sees exactly its unit's inputs and produces its unit's outputs. What
  happens inside (an amax, a division, packing two FP4 values per byte) is
  invisible to the planner, as the rounding of a cast is today.

Three rules decide what may become a unit function (the admission line):

1. **A unit is never split.** Every cut the planner makes (runs, chunks,
   staging rounds, padding trimmed, allocation boundaries) falls on a unit
   boundary; a unit lies in one allocation.
2. **`f` reads only its own unit.** No reduction across units (a tensor-wide
   amax, a softmax, a prefix sum) and no output whose size depends on values.
   A tensor-wide quantity is an input (a scalar source), computed elsewhere.
3. **`f` comes from a closed catalog**, each entry with one host
   implementation shared by host code and kernels (`convert.hpp`) and a
   torch recipe it matches bit for bit (NaN for NaN). No user code.

What does not pass stays outside copyengine. What passes is a new catalog
entry, not a change to the IR.

### Planning

- An op carries its unit size, its extra sources (scales in) and extra
  destinations (scales out), each an endpoint and an access. Its footprint is
  one interval list per side; dependencies and waves are computed over all
  of them.
- Lowering, merging and 2-D recovery work on units as they do on elements
  (a unit is a larger element), so a group of copies quantized the same way
  still merges and batches.
- Element-wise copies are unchanged: `g = 1`, one source, one destination.

### Catalog, first version

**What bit-exact means here.** copyengine's bit-exact guarantee is about
copies: moving and converting values gives torch's result. A catalog entry
computes, and computation has no single torch result: the order and form of
the arithmetic decide the last bit, and torch's own result depends on the
device (below). For catalog entries the guarantee is that copyengine's host
and GPU paths and the entry's recipe agree bit for bit, on every device;
torch code computing the same formula another way may differ in the last
bit, which is normal for computation and is said so in the README.

Every entry has a torch recipe below (`copyengine/_quant.py` holds the one
copy, which is also the torch baseline); `x` is the input widened to float32
(exact for bf16 / fp16), arithmetic is float32 without FMA, casts round to
nearest even. Computation takes the common optimized forms: a division by
a constant or by a unit's scale is a product with a float32 reciprocal
(`amax * (1 / 448)`, `x * (1 / scale)`, one reciprocal per unit). That is
also the one form torch evaluates alike on every device: it divides
`tensor / scalar` by a reciprocal product on the GPU but truly on the CPU.
For MX scales (powers of two) the product equals the division.

**Scaled formats** (`fp8_e4m3`, `fp8_e5m2`, `int8`; `qmax` 448, 57344, 127):

- Dynamic quantization, per unit (outputs `q` and `scale`):

      amax  = x.abs().amax(-1, keepdim=True)        # over the unit; NaN propagates
      scale = amax.clamp(min=eps) * (1 / qmax)       # eps = 1e-12 unless given
      q     = (x * (1 / scale)).clamp(-qmax, qmax).to(fp8)
            # int8: torch.round(x * (1 / scale)).clamp(-127, 127).to(torch.int8),
            #       NaN -> 0 (torch leaves that conversion undefined)

- Static quantization: the same `q` with `scale` given (one per unit, or one
  scalar).
- Dequantization: `y = (q.float() * scale).to(out_dtype)`.

**INT4**, packed two per byte (element 2i in the low nibble), NaN -> 0:

- `int4`, symmetric:

      scale = amax.clamp(min=eps) * (1 / 7)
      q     = torch.round(x * (1 / scale)).clamp(-8, 7)  # two's complement nibbles

- `uint4`, asymmetric with a zero point (torchao's affine form), outputs `q`,
  `scale` and `zero` per unit:

      lo    = x.amin(-1, keepdim=True).clamp(max=0)       # the range includes 0
      hi    = x.amax(-1, keepdim=True).clamp(min=0)
      scale = (hi - lo).clamp(min=eps) * (1 / 15)
      zero  = torch.round(-lo * (1 / scale)).clamp(0, 15)
      q     = (torch.round(x * (1 / scale)) + zero).clamp(0, 15)
      y     = (q - zero) * scale                          # dequantization

**MX formats** (`mxfp8_e4m3`, `mxfp8_e5m2`; OCP MX v1.0): units of 32, an
E8M0 scale per unit, `emax` 8 / 15:

      m, e  = torch.frexp(amax)                       # amax = m * 2**e, m in [0.5, 1)
      shared = (e - 1 - emax).clamp(-127, 127)        # floor(log2(amax)) - emax
      shared = where(amax == 0, -127, shared)
      q      = (x / ldexp(1.0, shared)).clamp(-max, max).to(fp8)
      scale  = (shared + 127).to(uint8)  # as float8_e8m0fnu
      # amax NaN or Inf: scale 0xFF (NaN) and every q NaN

**NVFP4**: units of 16, an E4M3 scale per unit, and a float32 global scale
`gs` given per tensor (computed elsewhere: rule 2):

      s  = (amax * (1 / 6) * (1 / gs)).clamp(max=448).to(float8_e4m3fn)
      q  = where(s == 0, 0, x * (1 / (s.float() * gs))).clamp(-6, 6) -> E2M1 (nearest even)
      packed two per byte, element 2i in the low nibble (float4_e2m1fn_x2)

Each recipe is written once in the tests as torch code
(`tests/python/test_quant_ref.py`); the host and GPU paths must reproduce it
bit for bit, on random data, on the edges (zero units, NaN, Inf, values at
and beyond the format's maximum, subnormal amax), and on units built to land
on the format's rounding ties, where the rounding direction and the form of
the arithmetic (`x / scale` against `x * (1 / scale)`) show.

### Strategies

- **On the GPU**: a tile kernel, one warp per unit (a block for long units),
  reading and writing device memory, or pinned host memory directly where
  zero-copy is admitted.
- **Compress, then move** (GPU to host): quantize into device staging, then
  DMA the smaller `q` and `scale`.
- **Move, then compress**: DMA the raw data, then quantize on the side that
  receives it (the host executor's threads for host destinations).
- The torch recipe is the baseline where the caller's tensors allow it
  (the same rules as today's native copies); the tuner measures the rest.

### API

```python
ce.quantize(x, q, scale, fmt="fp8_e4m3", group=128)              # dynamic: writes scale
ce.quantize(x, q, scale, fmt="fp8_e4m3", group=128, static=True) # scale given (or broadcast)
ce.quantize(x, q, scale, zero, fmt="uint4", group=64)            # asymmetric: zero points too
ce.quantize(x, q, scale, fmt="nvfp4", global_scale=gs)
ce.quantize(kv, q, scale, fmt="fp8_e4m3", group=128,
            x_index=pages, index=slots)                           # gather pages, write cache blocks
ce.dequantize(q, scale, out, fmt="fp8_e4m3", group=128, index=slots, x_index=pages)
```

- Shapes: x `[..., D]` (up to three leading dimensions, any strides); q
  `[..., D]` (packed formats `[..., D / 2]`); scale and zero `[..., D / group]`.
- `x_index` / `index` select the rows of the first dimension of x / of q,
  scale and zero: host indices are checked when queued and read when the
  copy runs (new indices reuse the plan); GPU index tensors stay there (an out-of-range unit is skipped, and
  `synchronize()` raises), and step plans rebind them per call.
- The tensors are on the host, or on one GPU with the rest in pinned host
  memory: the kernel reads and writes the host side directly (admitted
  zero-copy), so an offload quantizes and moves in one pass.
- Calls in a scope with the same format and direction run as one launch.
- Units run along the last dimension of the view given, with any stride: a
  grouping across tokens (a V cache quantized per channel over tokens) is the
  transposed view, `ce.quantize(v.transpose(-1, -2), q.transpose(-1, -2), ...)`.
- Partial pages: as in vLLM's and LMDeploy's caches, tokens that do not hold
  data are not units to quantize (pass the valid rows with `index=`); a group
  spanning tokens is quantized once it is complete, the incomplete tail staying
  in full precision with the caller (as KIVI keeps a residual). copyengine adds
  no masks: a unit with a value-dependent number of elements would break the
  admission line.

### Built so far

- Units, extra footprints (scale, zero point) and grouping by format in the
  planner; element copies unchanged.
- Every catalog entry on the host and in a GPU kernel per format and
  direction (one warp per unit), bit for bit with its recipe on both.
- Dynamic and static scales, gathers and scatters by index, GPU and pinned
  host memory in one op, step plans.

- Tensors split between a GPU and pinned host memory have two strategies,
  measured against each other and the recipe: `tile` (the kernel reads and
  writes the host side in place, zero-copy) and `tile_staged` (what the
  kernel reads goes to device staging by DMA first, what it writes comes back
  by DMA after: compress then move, move then decompress). Staging is offered
  where the host tensors are compact (read spans at most twice the bytes
  they hold, written ones dense). A host tensor whose rows host indices
  select (the slots of a host pool) is staged row by row, one batched DMA per
  tensor and direction, and the kernel runs on the compact rows; GPU tensors
  keep their indices (paged offload: `x_index` over GPU pages, `index` over
  host slots). Not staged: host rows selected by a GPU index tensor, and an
  index shared by host and GPU tensors.
- Staging runs in chunks of rows of the first dimension (about a quarter of
  the bytes each, above 2 MB) that alternate between two halves of the
  staging buffer: a chunk's inputs move in on a second stream while the
  previous chunk's kernel runs, its outputs move out while the next one's
  does, and the second stream joins the caller's before the call returns.
  Rows whose host extents interleave (transposed host views) stay one piece.
  A row (or such an op) must fit in half the staging budget.

- Tile kernels keep their descriptor in shared memory (in registers it
  would take some 60 of them and spill), cache a thread's values in
  registers through unrolled loops, and read codes four at a time. Where few
  SMs run them they are latency-bound: what helps is bytes in flight at the
  same occupancy. A thread takes 8 consecutive values of a unit (units of
  32 values and more; 4 below, so a load still covers few units), and
  constant divisions and NVFP4's 1 / global scale are computed once.

### Still to come in 0.4

- Tuning on sm90 and later from measurements there: the bulk segment size,

## 2. TMA / cp.async

A new strategy, `bulk`, for pure copies on one GPU: rows are cut into
segments and moved global -> shared -> global through four buffers per block
(one warp), so later segments load while earlier ones store. Segments are
sized per GPU (at most 8 KB) so that eight blocks fit in an SM's shared
memory: under `max_sms` the bytes in flight come from the blocks that fit on
the few SMs. `CE_BULK_SEG` overrides the size (diagnostics on new hardware).

- **sm90 and later**: one thread drives TMA bulk copies (`cp.async.bulk`
  with an mbarrier per buffer; a buffer is reloaded once the store before
  the newest has read it, so a store stays in flight). Few threads keep many bytes in flight, which
  is what copies confined to a few SMs (`max_sms`) lack.
- **sm80 to sm89**: the warp uses `cp.async` (16-byte asynchronous loads).
- Rows, widths or pitches not 16-byte aligned take the plain warp copy;
  older GPUs never get the strategy.
- Admitted per GPU by a verified test copy (rows of several segments, with
  pitches); `stats()["cuda"][i]["bulk"]` reports `"tma"`, `"cp.async"`, or
  why not. Offered for groups of at least 1 MB and measured like any other
  strategy (it keeps no advantage it does not show).

Next, once measured on sm90+: TMA tensor maps for 2-D units (a tile IR unit
is a TMA box), and the tile kernels reading through TMA.

## Testing

As in 0.3: every catalog entry against its torch recipe, bit for bit, on
the host and on the GPU; planner tests that no cut splits a unit; the GPU
matrix (`just test-gpu-matrix`) on each GPU generation before a release.
