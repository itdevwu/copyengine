# copyengine 0.5 design

Status: draft, updated as the design settles. 0.5 has one promise and one
step in the model:

1. **copyengine with torch.compile is never worse than torch.compile
   alone.** Compiled graphs are left alone, copyengine calls inside a
   compiled region do not split its graph, and there they are measured
   against the code torch.compile generates for the same operation.
2. **Boxes and composition.** A unit becomes a box (rows of consecutive
   elements at a fixed pitch), which is also what TMA moves; and copies
   compose: a chain of views, rearrangements (einops), gathers, conversions
   and a write into an existing tensor plans and runs as one copy.

It also carries what 0.4 left open: explicit copies with GPU indices and a
host destination, quantization kernels specialized for the common contiguous
layout (where torch.compile's generated kernels were ahead), and the first
plan of a step with hundreds of tensors.

## 1. torch.compile

### Graphs stay whole

The explicit API is already a set of torch custom ops (`torch.ops.copyengine.*`,
stable ABI, with meta kernels and mutation annotations); what split graphs
was the Python around them (engine lookup, argument checks). Under
`torch.compiler.is_compiling()` the API emits the op directly, with the
engine as an integer argument, so Dynamo records one node per call. The
quantization API gets ops of its own. Calls whose arguments are Python
objects Dynamo cannot trace (lazy views) are lowered to tensors and integers
before the op.

Module-level calls inside a compiled region use one process-wide engine
(engine handle 0, created by the core on first use: no Python engine is
traced); `ce.compiled_stats()` reports it. A form no op takes (host index
lists, a lazy `flip`) calls a dynamo-disabled eager path: the graph breaks
there and the results are the same.

### Warm when the model is warm

copyengine explores on the first runs of a copy pattern, which inside a
compiled model are its warmup runs, and locks. CUDA graph trees record
after one or two warmups: inside a capture an op takes its locked strategy,
else the profile's, else its prior choice (it never explores there).

### The baseline inside a compiled region

Outside torch.compile the baseline is torch's eager copy. Inside a compiled
region it is what torch.compile makes of the same operation. The first time
a call of a kind and layout is traced, `_compiled.decide` (a constant of the
graph: `assume_constant_result`) measures on a worker thread, since Dynamo
traces only the calling thread: real tensors of that layout; the op's torch
equivalent (a copy, `index_select`, `index_copy_`, the quantization recipe)
traced by `make_fx` and compiled by Inductor directly (`torch.compile` there
would wait for Dynamo's compile lock, held by the tracing thread); bits
checked against copyengine's (NaN for NaN); then both timed, copyengine
explored and locked first. The trace emits the torch equivalent (Inductor's
code, free to fuse with its neighbours) unless copyengine is at least 5%
faster: ties keep the baseline. A baseline with other bits (a recipe
Inductor rounds differently) or that does not compile is not admitted.
Decisions and their reasons are kept per process (`compiled_stats()
["baselines"]`); `CE_COMPILE_BASELINE=0` skips the measurement. Calls with
symbolic sizes (dynamic shapes) take copyengine's op without measuring:
traced code cannot tell a symbolic int from an int, so the compiler itself
is asked (`comptime`), and nothing symbolic reaches the constant function.
`bench/bench_compile.py` shows torch.compile alone against compile + ce.

## 2. Boxes

A unit is `rows x width` elements: `width` consecutive elements per row,
rows at a pitch. Element copies are 1x1 boxes and 0.4's units 1-row boxes,
so nothing changes for them. No cut splits a box: run merging, 2-D recovery,
staging rounds and allocation boundaries treat a box as indivisible; its
footprint is its rows.

- **Lowering to TMA** (sm90 and later), strategy `tma2d`: each 2-D block of
  a pure device copy (width bytes x rows, a pitch per side) is a pair of
  uint8 tensor maps, encoded on the host and resident with the plan, moved
  box by box (up to 256 bytes x 8 KB / width rows) through two shared
  buffers: one TMA operation per box where the row-wise `bulk` copy issues
  one per row segment, which matters for narrow rows (a KV head of 256
  bytes). Edge boxes need no special case (loads past the block fill zeros,
  stores are clipped). Admitted by a verified pitched test copy
  (`stats()["cuda"][i]["tma2d"]`), offered for groups of 2-D blocks of at
  least 1 MB whose addresses and pitches are 16-byte aligned, and measured
  like the other strategies. Older GPUs keep the row-wise strategies.
- **Catalog**: block FP8 / INT8 with one float32 scale per box (`128 x 128`
  as DeepSeek-V3 stores weights): the scaled formats' formula over a box's
  values, recipes `quantize_block` / `dequantize_block` in
  `copyengine/_quant.py`. `ce.quantize(w, q, scale, fmt=..., block=(bh, bw))`
  takes x and q `[..., M, N]` and scale `[..., M / bh, N / bw]`.
- **In tile ops** a box unit is `bh` rows of `g` values with a pitch per
  tensor; footprints include the box rows; kernels run a box per warp (a
  pass for the amax, one for the codes; 4 values per access where aligned);
  staging and step plans treat it like any unit.

## 3. Composition

`ce.lazy(x)` accepts einops' rearrangements (as an einops backend):
`rearrange`, `repeat` and the reshapes they imply compose into the lazy
view without materializing anything, then compose with `index_select`,
dtype conversion or quantization, and the write into the destination:

```python
src = einops.rearrange(ce.lazy(kv), "(blk tok) h d -> blk h tok d", tok=16)
ce.copy_(cache, src.index_select(0, pages))   # one planned copy
```

einops finds the backend by itself (`copyengine/_einops.py`, a subclass of
its `AbstractBackend`). Inside torch.compile regions einops' functions may be
graph nodes (`allow_in_graph`) that a lazy view cannot enter: `ce.rearrange`
/ `ce.repeat` take the same patterns and, there, compute the view ops as a
constant of the graph (einops run on a recorder of shapes) and apply them. Reshapes no torch view expresses still compose: old
and new dimensions pair into groups of equal size, and a group of one new
dimension over several old ones (`(t h)` after a transpose, a merge after a
gather by host indices) becomes a table of offsets, as a host index table
does. A group that both splits and merges is not a view. `repeat` into a new
axis broadcasts, into an existing one reads values again (a gather); `reduce`
raises (a reduction).

Inside a step plan, a tensor the step allocates and drops is a temporary:
copies into it followed by copies out of it compose into direct copies, and
the tensor is not written. A temporary is GPU memory the copies use that is
no argument and that torch's allocator holds free once the step returned
(after the engine dropped its own references, the baselines' tensors): the
step allocated it and let it go. Composition works on pure copies' byte
runs (each byte read from the temporary takes the source of the latest byte
written there); anything else touching the temporary, or a byte read before
it is written, leaves the step unreplayable as before. The composed copies
are planned anew, on the strategies the engine locked for their kind.

## 4. Left open by 0.4

- Explicit copies with GPU indices into host memory.
- Quantization kernels: where the units of a row of the first dimension are
  back to back in every tensor (KV pages, contiguous tensors), a unit's
  address takes one division (the row, through its index if any) and
  constant steps, instead of three divisions and per-dimension strides.
- Planning a step of hundreds of tensors the first time: most of a new
  engine's first flush was admitting the GPU (loading the kernels' module,
  the verified test copies), repeated by every engine and leaking a module
  each time. Admission is now once per device and process; engines share the
  module and the verdicts. What remains is planning itself (about a
  millisecond for 576 tensors).
