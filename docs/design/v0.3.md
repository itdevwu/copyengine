# copyengine 0.3 design

Status: draft, updated as the design settles. 0.3 builds two things:

1. **Device-parametric plans**: plan a step once, replay it with new tensors
   and indices, including indices that live on the GPU, inside CUDA graphs,
   with the dimensions that change per step handled automatically.
2. **Bandwidth QoS, first version**: copies that run as a rate-limited
   background task instead of taking all the PCIe or memory bandwidth.

## 1. Device-parametric plans

### Problem

A step that copies the same pattern every iteration (KV blocks of the
scheduled requests, per-layer offload, graph-input refresh) pays planning or
per-call host overhead each time, and `freeze()` only replays the exact same
buffers and indices. Index tensors on the GPU are copied to the host (a
device synchronization) because the planner needs concrete values.
Frameworks also need one CUDA graph to serve every step, whose block ids
differ.

### API

```python
step_plan = eng.plan(step)                 # step(engine, *args) issues ce copies
step_plan(kv_cache, host_kv, block_ids)    # first call: traced and planned
step_plan(kv_cache, host_kv, other_ids)    # later calls: rebind, no planning
```

- `eng.plan(step, dynamic=None)`: like `torch.compile`'s `dynamic`.
  - `None` (default): the first call specializes on every size. When a later
    call changes a size (an index length, a block count), that dimension
    becomes dynamic and is planned once more by size class; nothing has to be
    marked.
  - `True`: every size that can vary is dynamic from the first call.
  - `False`: exact sizes; a change plans again.
- `ce.dynamic(x, dim)`: optional, declares ahead of time that a dimension
  varies (like `torch._dynamo.mark_dynamic`), saving one re-plan.
- A plan is callable inside `torch.cuda.graph`, and inside
  `scope(stream=...)`.

### What a parameter is

- **Tensor bases**: every tensor argument is rebound by its data pointer.
- **Index tables**: an index argument (list, numpy array, CPU tensor or CUDA
  tensor) is a table parameter. CUDA index tensors stay on the device.
- **Dynamic sizes**: the length of a dynamic dimension, inside its size class.

Everything else (dtypes, devices, strides of static dimensions, the
structure of the step's ce calls) is part of the plan. **Guards** check it on
each call: dtype, device, shape of static dimensions, strides, 16-byte
alignment of each base (vector paths depend on it), and which arguments
alias. A failed guard plans again (bounded by a cache; the oldest plan
goes first).

### Size classes

A dynamic dimension of length n is planned at the next power of two (minimum
16). The kernels take the true length as a parameter and skip the tail, so
one plan, one tuning decision and one captured graph serve every length in
the class. Static dimensions are tuned at their exact size, as today.

### Device-side tables

A table term of an `Access` can refer to a parameter slot instead of host
values. Kernels read the index from that slot, so the planner never needs
the values: only kernel strategies (`kernel`, `fused`) can run such a
statement; DMA strategies need host addresses. Checks that need values move
to the device:

- **Bounds**: a kernel that meets an out-of-range index skips it and sets an
  error flag in device memory; the next synchronizing call (`barrier`,
  `synchronize`, `h.synchronize()`) raises. Open question: whether to read
  the flag after every replay in debug mode (`CE_SYNC=1`).
- **Duplicate scatter targets**: not detected on the device. The explicit
  scatter API documents that duplicates with device indices are undefined,
  as torch's `index_copy_` does.

### Implementation of device-side tables

- **IR.** A `Term` holds either host values or a *device table*: pointer,
  length, element stride (in indices) and device. `slice` on such a dimension
  moves the pointer and multiplies the stride (`flip` negates it);
  operations that need values (`select`, `index_select` of it) raise
  `NeedsMaterialize`.
- **Ops without runs.** A statement with a device table cannot be lowered to
  runs. It becomes an op whose read / write footprint is its whole source /
  destination allocation (conservative, so dependencies stay exact enough
  without values) and whose only executable form is its `Form`.
- **Plan key.** Table pointers are per-call values, like native payloads:
  they are not part of the op fingerprint, only "dimension k reads a device
  table". Changing indices therefore hits the same plan.
- **Execution.** `Form` gains per-dimension table pointers and strides on each
  side, and the bound to check against; the statement kernel reads the index
  for those dimensions. Statement bases and table pointers go to the device
  per call through the upload ring (the parameter block below replaces this
  for graph capture).
- **Errors.** Each device has an error word; a kernel that meets an index
  outside its bound skips the element and sets it; `synchronize` reads and
  clears it and raises `ValueError` (the existing invalid-argument error, so
  the C ABI is unchanged).
- **Strategies.** Such a group runs only as `fused` (the statement kernel),
  or as the native torch replay where one exists (the A/B decides, as
  everywhere). The torch replay keeps torch's own out-of-range behavior.
- **Python.** `gather`, `scatter_` and `Lazy.index_select` keep CUDA index
  tensors on the device (cast to int64 on the device when needed); host
  indices take the existing path. Explicit `gather` / `scatter_` on CUDA
  tensors go through the stable-ABI ops `copyengine::gather_` /
  `scatter_` (FrontendApi `copy_indexed`), whose baselines are
  `index_select(out=)` and `index_copy_`.
- **Per-call bases.** The bases of the last few table-pointer sets of a batch
  stay on the device (written by a kernel whose parameters carry them, in
  stream order), so calls with the same index tensors launch only the copy
  kernel.
- **Graph capture.** Under capture the bases are written by kernel nodes
  whose parameters carry them (no host buffer outlives the capture), so a
  graph replays with new index values in the same index tensors. New index
  *tensors* in a graph need the parameter block below.

### Parameter block and replay

Each plan owns a parameter block in device memory: bases, table pointers
and lengths. A call fills a pinned host copy of the block and enqueues one
H2D copy of it ahead of the plan's launches; kernels read their arguments
from the block. Inside a CUDA graph that copy is a node, so the same graph
replays with new parameters: the host writes the pinned block before
`graph.replay()`. The pinned block is double-buffered and guarded by an
event, so a replay still in flight is never overwritten.

### Layers in one launch

Statements with the same structure share one fused batch whatever their
bases, so L layers allocated separately (a `List[Tensor]` KV cache, FSDP
shards) already run as one kernel launch; their bases need not advance by
a constant stride. Folding equal-stride statements into one statement with
an extra dimension would only save planning, and is done only if planning
cost shows up (`stats()["plan_us"]`).

### Implementation of step plans

- **Arguments.** Tensors, sequences of tensors (`TensorList`, one level),
  index tensors (host or CUDA) and Python scalars, positional or keyword.
  All memory the step's copies touch must come from its arguments: a tensor
  allocated inside the step is a new address each call (an error names it).
- **Trace.** The first call for a guard key runs `step` with an engine
  scope open and keeps the plan of its flush (as `freeze()` does). Every
  allocation an op touches is a *slot* of the plan (device, byte range); each
  slot is matched to the argument whose storage it is. Only the copies are
  replayed: other code in `step` runs at trace time only.
- **Guard key.** Per tensor: dtype, device, shape, strides, storage offset,
  storage size, data pointer modulo 16, and which arguments share a storage
  (slot identity). Per sequence: its length. Per index argument: host or
  device, and its length. Scalars: their values. A failed guard traces again
  (LRU of traced plans). Lengths are exact in this piece: a new length traces
  again (planning a step is cheap and tuning decisions are shared by bucket);
  size classes follow only if re-tracing shows up.
- **What a call rebinds.** Device index tables (pointers are per-call
  values already) and the step's tensors *by identity*: the guard includes
  each slot's base address, so the same buffers replay without planning and
  a moved buffer traces again (an LRU of traces keeps double-buffered
  arguments hitting). This covers serving steps whose caches and pools are
  long-lived and whose per-step inputs are index tensors.
- **Moving buffers (next piece).** Rebinding moved tensors by slot deltas:
  the plan keeps its traced addresses; a call computes per slot the delta to
  the current base; host-issued strategies add it while issuing, kernel
  tables carry each entry's slots and kernels add `delta[slot]` from the
  plan's parameter block (written with `ce_put`; for graphs, a pinned copy and
  one H2D node, so `bind` + `graph.replay()` rebinds); staging strategies keep
  identity guards. Built only if identity guards miss in practice.
- **No regression.** A replay skips the step's Python and the planner, but
  the baseline is the step itself run as plain torch code: a plan alternates
  replays with plain runs (paired, end to end, after its tuning settled) and
  keeps replaying only if that clearly wins, like a scope call site.

### Tuning

Decisions are keyed by plan and size class instead of only by bucket. A
plan replays its decided strategies without the per-flush tuner lookup;
online re-checks sample whole replays.

## 2. Bandwidth QoS, first version

### Problem

A large offload or prefetch takes all the link or memory bandwidth it can,
and compute or collective communication running at the same time slows
down. Copy engines have no rate control, and `max_sms` limits SMs, not
bandwidth.

### API

```python
with ce.scope(stream="copy", bandwidth=8e9) as h:   # at most ~8 GB/s
    ...
eng = ce.Engine(bandwidth=8e9)                       # every copy of this engine
```

`bandwidth` (bytes per second) applies to every copy the scope queues that
touches a GPU, including inner scopes without their own limit, and to the
explicit API. Host-to-host copies, and copies copyengine leaves to torch
(declined at interception), are not limited; neither, in this version, are
copies with device indices (pacing cuts runs, and they have none). Without it
nothing changes.
`CE_DISABLE=1` also turns limits off.

### What runs

A limited op never runs as torch's copy and never shares a group with
unlimited ops or ops under another limit (the limit is part of its
fingerprint, so it also gets its own plans). Its group runs one strategy,
`paced`; the tuner does not race it against full-speed candidates, since its
objective is the limit, not the shortest time.

- **Pacing.** `paced` cuts the group's runs into chunks of about 250 us at
  the limit (64 KiB to 16 MiB). Before each chunk a one-thread kernel
  (`ce_pace`) reserves the chunk's slot on a per-GPU, per-direction
  word in device memory (H2D, D2H, on-device / peer) with a CAS on the GPU's
  global timer, and sleeps (`__nanosleep`) until the slot starts. Pacing
  stays on the GPU: no host thread and no host waits; concurrent limited
  streams on one GPU and direction share the budget; idle time is not
  saved up, so bursts are at most one chunk.
- **Per chunk, the cheapest path that suits its layout.** Large rows: DMA
  (`runs`, or `batch` for many rectangles). Small rows (under 4 KiB): a
  kernel on the device, or a **zero-copy** kernel that reads or writes
  pinned host memory directly through unified addressing, with streaming
  loads and stores (`ld.global.cs` / `st.global.cs`, `ce_bytes_cs`) so it
  does not evict the compute's data from L2; conversions use the typed
  kernels the same way. Pageable host memory goes through staging or bounce
  buffers. Chunks never cross an allocation boundary (they are cut from the
  group's runs, which never do).
- **Zero-copy admission.** Used only after a test copy through pinned host
  memory comes back exact on that GPU, and only for host allocations the
  driver maps at the same address on the device (checked per allocation at
  planning); `stats()["cuda"][i]["zero_copy"]` reports it.
- **CUDA graphs.** A limited copy captured into a graph records its pacing
  kernels and chunk copies, so replays are paced too. Pacing state and
  kernel tables are set up on first use: run the copy once before
  capturing; a limited copy that cannot be recorded (pageable memory) raises
  `Unsupported` instead of running unlimited.
- **`max_sms`.** Kernel chunks launch within the engine's SM limit; the
  pacing kernel is one thread.

### Not in this version

The chunk duration is fixed rather than tuned online, the zero-copy grid is
not sized from the limit (pacing already bounds the rate), and DMA is not
measured against zero-copy per layout: each chunk takes its path from its
row size.

## 3. Caches and planning cost

The plan, statement and safety caches are LRU (capacity from `plan_cache`,
4x for statements and safety checks): a working set slightly larger than the
cache loses only its coldest entries. Planning time on a plan-cache miss is
reported (`stats()["plan_us"]`, and per flush). It is paid by native and ce
strategies alike inside a flush, so it does not bias their A/B; it matters
against copies that bypass the queue (`native_now`), which this version only
reports.

## 4. Pinned memory from the framework

copyengine's own pinned host buffers (bounce buffers, the upload ring) come
from the framework's pinned allocator when one is registered, as its device
memory already does (`DeviceAllocator::host_alloc` / `host_free`; for torch,
the caching host allocator behind `pin_memory()`). copyengine frees such a
buffer only after the events of its own work on it completed, so the
framework may reuse it at once. One-off admission tests still use the driver.

## Testing

On the local RTX 3060 (sm86): everything above. Parametric plans: replays
against torch on randomized steps, guard failures, dynamic transitions, CUDA
graph replay with new parameters, device-index bounds errors, folding on and
off. QoS (`tests/python/test_bandwidth.py`): reached bandwidth within a loose
tolerance of the limit per direction, results against torch (zero-copy rows,
conversions, pageable memory), nested scopes, async scopes, pacing inside a
CUDA graph replay. Other GPUs (sm89,
sm120) are checked through the release hardware run.

## Not in 0.3

Anything not described above, in particular the parts of the roadmap
planned for later versions.
