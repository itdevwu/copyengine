# copyengine 0.3 design

Status: draft, updated as the design settles. 0.3 builds two things:

1. **Device-parametric plans**: plan a step once, replay it with new tensors
   and indices, including indices that live on the GPU, inside CUDA graphs,
   with the dimensions that change per step handled automatically.
2. **Bandwidth QoS, first version**: copies that run as a rate-limited
   background task instead of taking all the PCIe or memory bandwidth.

## 1. Device-parametric plans

### Problem

A step that copies the same pattern every iteration (KV blocks of the
scheduled requests, per-layer offload, graph-input refresh) pays planning or
per-call host overhead each time, and `freeze()` only replays the exact same
buffers and indices. Index tensors on the GPU are copied to the host (a
device synchronization) because the planner needs concrete values.
Frameworks also need one CUDA graph to serve every step, whose block ids
differ.

### API

```python
step_plan = eng.plan(step)                 # step(engine, *args) issues ce copies
step_plan(kv_cache, host_kv, block_ids)    # first call: traced and planned
step_plan(kv_cache, host_kv, other_ids)    # later calls: rebind, no planning
```

- `eng.plan(step, dynamic=None)`: like `torch.compile`'s `dynamic`.
  - `None` (default): the first call specializes on every size. When a later
    call changes a size (an index length, a block count), that dimension
    becomes dynamic and is planned once more by size class; nothing has to be
    marked.
  - `True`: every size that can vary is dynamic from the first call.
  - `False`: exact sizes; a change plans again.
- `ce.dynamic(x, dim)`: optional, declares ahead of time that a dimension
  varies (like `torch._dynamo.mark_dynamic`), saving one re-plan.
- A plan is callable inside `torch.cuda.graph`, and inside
  `scope(stream=...)`.

### What a parameter is

- **Tensor bases**: every tensor argument is rebound by its data pointer.
- **Index tables**: an index argument (list, numpy array, CPU tensor or CUDA
  tensor) is a table parameter. CUDA index tensors stay on the device.
- **Dynamic sizes**: the length of a dynamic dimension, inside its size class.

Everything else (dtypes, devices, strides of static dimensions, the
structure of the step's ce calls) is part of the plan. **Guards** check it on
each call: dtype, device, shape of static dimensions, strides, 16-byte
alignment of each base (vector paths depend on it), and which arguments
alias. A failed guard plans again (bounded by a cache; the oldest plan
goes first).

### Size classes

A dynamic dimension of length n is planned at the next power of two (minimum
16). The kernels take the true length as a parameter and skip the tail, so
one plan, one tuning decision and one captured graph serve every length in
the class. Static dimensions are tuned at their exact size, as today.

### Device-side tables

A table term of an `Access` can refer to a parameter slot instead of host
values. Kernels read the index from that slot, so the planner never needs
the values: only kernel strategies (`kernel`, `fused`) can run such a
statement; DMA strategies need host addresses. Checks that need values move
to the device:

- **Bounds**: a kernel that meets an out-of-range index skips it and sets an
  error flag in device memory; the next synchronizing call (`barrier`,
  `synchronize`, `h.synchronize()`) raises. Open question: whether to read
  the flag after every replay in debug mode (`CE_SYNC=1`).
- **Duplicate scatter targets**: not detected on the device. The explicit
  scatter API documents that duplicates with device indices are undefined,
  as torch's `index_copy_` does.

### Implementation of device-side tables

- **IR.** A `Term` holds either host values or a *device table*: pointer,
  length, element stride (in indices) and device. `slice` on such a dimension
  moves the pointer and multiplies the stride (`flip` negates it);
  operations that need values (`select`, `index_select` of it) raise
  `NeedsMaterialize`.
- **Ops without runs.** A statement with a device table cannot be lowered to
  runs. It becomes an op whose read / write footprint is its whole source /
  destination allocation (conservative, so dependencies stay exact enough
  without values) and whose only executable form is its `Form`.
- **Plan key.** Table pointers are per-call values, like native payloads:
  they are not part of the op fingerprint, only "dimension k reads a device
  table". Changing indices therefore hits the same plan.
- **Execution.** `Form` gains per-dimension table pointers and strides on each
  side, and the bound to check against; the statement kernel reads the index
  for those dimensions. Statement bases and table pointers go to the device
  per call through the upload ring (the parameter block below replaces this
  for graph capture).
- **Errors.** Each device has an error word; a kernel that meets an index
  outside its bound skips the element and sets it; `synchronize` reads and
  clears it and raises `ValueError` (the existing invalid-argument error, so
  the C ABI is unchanged).
- **Strategies.** Such a group runs only as `fused` (the statement kernel),
  or as the native torch replay where one exists (the A/B decides, as
  everywhere). The torch replay keeps torch's own out-of-range behavior.
- **Python.** `gather`, `scatter_` and `Lazy.index_select` keep CUDA index
  tensors on the device (cast to int64 on the device when needed); host
  indices take the existing path. Explicit `gather` / `scatter_` on CUDA
  tensors go through the stable-ABI ops `copyengine::gather_` /
  `scatter_` (FrontendApi `copy_indexed`), whose baselines are
  `index_select(out=)` and `index_copy_`.
- **Per-call bases.** The bases of the last few table-pointer sets of a batch
  stay on the device (written by a kernel whose parameters carry them, in
  stream order), so calls with the same index tensors launch only the copy
  kernel.
- **Graph capture.** Until the parameter block exists, the per-call upload
  is not capture-safe: under capture such a group takes the native replay.

### Parameter block and replay

Each plan owns a parameter block in device memory: bases, table pointers
and lengths. A call fills a pinned host copy of the block and enqueues one
H2D copy of it ahead of the plan's launches; kernels read their arguments
from the block. Inside a CUDA graph that copy is a node, so the same graph
replays with new parameters: the host writes the pinned block before
`graph.replay()`. The pinned block is double-buffered and guarded by an
event, so a replay still in flight is never overwritten.

### Folding statements across layers

Within one traced step, consecutive statements whose bases advance by a
constant stride (one per layer) and that are otherwise equal fold into one
statement with an extra dimension: L copies become one kernel. Folding is
attempted at planning time and kept only where the pattern holds for every
statement in the run; it stops at the first break.

### Tuning

Decisions are keyed by plan and size class instead of only by bucket. A
plan replays its decided strategies without the per-flush tuner lookup;
online re-checks sample whole replays.

## 2. Bandwidth QoS, first version

### Problem

A large offload or prefetch takes all the link or memory bandwidth it can,
and compute or collective communication running at the same time slows
down. Copy engines have no rate control, and `max_sms` limits SMs, not
bandwidth.

### API

```python
with ce.scope(stream="copy", bandwidth=8e9) as h:   # at most ~8 GB/s
    ...
```

`bandwidth` (bytes per second) applies to everything the scope issues, and
can also be set per engine (`Engine(bandwidth=...)`). Without it nothing
changes.

### Mechanisms

- **Paced DMA**: a transfer is cut into chunks; between chunks the copy
  stream runs a single-thread pacing kernel that sleeps (`__nanosleep`) for
  the time the next chunk is allowed. Pacing stays on the GPU: no host
  thread, no host waits, and it can be captured in a CUDA graph. Chunk size
  is tuned so the pacing kernels cost little.
- **Kernel copies over pinned host memory**: a new strategy where a kernel
  reads or writes pinned host memory directly (zero-copy through unified
  addressing), which also covers layouts DMA handles poorly. Its bandwidth
  is set by the number of thread blocks and the bytes per access; it uses
  streaming loads and stores (`ld.global.cs` / `st.global.cs`) so it does not
  evict the compute's data from L2. With `max_sms` it stays on its SMs.
- **Per direction**: H2D and D2H are paced separately; D2D uses the same
  mechanisms against memory bandwidth.

### Choosing the path

In a bandwidth-limited scope the tuner's objective changes from fastest to
"closest to the limit without exceeding it, at the lowest cost": it prefers
paced DMA (cheapest) and falls back to kernel copies where DMA cannot meet
the limit or the layout. It measures the bandwidth actually reached and
adjusts the chunk and grid sizes online.

## Testing

On the local RTX 3060 (sm86): everything above. Parametric plans: replays
against torch on randomized steps, guard failures, dynamic transitions, CUDA
graph replay with new parameters, device-index bounds errors, folding on and
off. QoS: reached bandwidth within a tolerance of the limit, compute slowdown
with and without a limit, pacing inside a CUDA graph. Other GPUs (sm89,
sm120) are checked through the release hardware run.

## Not in 0.3

Anything not described above, in particular the parts of the roadmap
planned for later versions.
